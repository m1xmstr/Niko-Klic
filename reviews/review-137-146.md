## What to learn

Find an exact filename, read saved evidence, rename without assuming contents changed, distinguish a literal message from a variable lookup, test a condition and an assertion, keep unknown facts unknown, check a model's example-following, count votes without treating agreement as truth, and choose read-only access for a read-only task.

Use the linked lessons for their prerequisites. An adult should supervise any terminal activity. Use invented data and a new disposable practice directory. The recordings used Linux for file operations, a separate macOS localhost Ansible environment, and an already installed local language model. These are separate exercises, not a hidden integrated automation system.

## 1. Locate and prepare the file — Linux

Requirements: an ordinary, non-root Linux user and the standard `find`, `cat`, `mv`, `chmod`, `stat`, and `sha256sum` commands. Do not run these permission exercises as root or on system or personal files.

Create an empty practice directory and the complete fictional fixture:

```sh
museum_dir=$(mktemp -d)
cd "$museum_dir"
mkdir art
printf 'STAR EXHIBIT\n' > art/star.txt
printf 'NOT THE STAR\n' > art/start.txt
printf '18:00 setup began\n18:01 label name wrong\n18:02 opening paused\n' > opening.log
printf 'STAR EXHIBIT\n' > wrong.txt
```

Predict before running each command:

```sh
find art -name 'star.txt'
cat opening.log
sha256sum wrong.txt
mv wrong.txt label.txt
test ! -e wrong.txt && printf 'old name absent\n'
cat label.txt
sha256sum label.txt
```

Recorded results: `find` returned only `art/star.txt`; `cat` displayed all three log lines in their saved order. The old name disappeared after the rename. The new file still contained `STAR EXHIBIT` followed by a newline. Its content SHA-256 was unchanged:

```text
bae1b1de09b2bce365a3b064e513f67133d79a397c8dde67ffc04abe2b33b59d
```

`find` returned a path, not the file's contents. The name pattern was exact in this example; `start.txt` did not match. The destination `label.txt` did not already exist. `cat` did not sort or interpret the log. The wrong-name entry suggested what to investigate; a saved statement is not automatically true. A separate shell confirmed the renamed contents.

## 2. Prepare the welcome — separate localhost Ansible

Requirements: an existing Ansible installation and a separate empty practice directory. The recording used ansible-playbook [core 2.18.5]. No remote inventory, facts gathering, privilege escalation, or device control is involved.

Save the complete playbook as `museum.yml`:

```yaml
- hosts: localhost
  connection: local
  gather_facts: false
  vars:
    guest: Nico
    ready: true
    exhibit: star
  tasks:
    - name: Literal example
      ansible.builtin.debug:
        msg: "Hello, guest!"
    - name: Lookup example
      ansible.builtin.debug:
        msg: "Hello, {{ guest }}!"
    - name: Ready greeting
      ansible.builtin.debug:
        msg: WELCOME READY
      when: ready
    - name: Check exhibit
      ansible.builtin.assert:
        that:
          - exhibit | length > 0
        fail_msg: EXHIBIT MISSING
        success_msg: EXHIBIT CHECKED
    - name: Opening message
      ansible.builtin.debug:
        msg: MUSEUM READY
```

Run syntax validation and the playbook:

```sh
ansible-playbook -i localhost, --limit localhost museum.yml --syntax-check
ansible-playbook -i localhost, --limit localhost museum.yml
```

The literal message is `Hello, guest!`; the lookup message is `Hello, Nico!`. Double curly braces request a variable value. In the recorded base case, the ready message and the final museum message both appeared.

Try these changes **one case at a time**, starting from the complete base playbook each time:

| Case | Change under `vars` | Recorded consequence |
|---|---|---|
| False condition | `ready: false` | The Ready greeting task was skipped; later tasks could still run. |
| Missing exhibit | `exhibit: ""` | The assertion failed with `EXHIBIT MISSING`; the Opening message task was never reached. |
| Changed visitor and name | `guest: Klic`, `exhibit: moon` | The lookup greeted Klic; the assertion passed and `MUSEUM READY` appeared. |
| Fresh base run | Restore Nico, true, star | The base results were reproduced independently. |

Every recorded run reported `changed=0`. Debug prints terminal text; it does not operate the illustrated entrance. The assertion checks only that the exhibit string has a nonzero length, not whether it is accurate or whether a real museum is safe. The failed run uses default failure handling, without `ignore_errors` or rescue.

## 3. Check the guide

### Missing evidence — scripted, not a model execution

Our fictional card says “Night Museum” and “Exhibit: star.” It gives no opening hour. The scripted answer is: “The card does not give an opening hour.” Ask for a reliable schedule instead of inventing six o'clock. A calm or confident answer cannot supply missing evidence.

### One example — actual local model recordings

Model: `llama3.2:3b`. Three independent local requests used temperature 0 and seed 141; each request contained only a system instruction and the example below. No training or model update occurred.

System instruction:

```text
Return only the new label.
```

User request:

```text
Make a museum label using the same bracket and capital-letter pattern as the example.
Example: fox -> [FOX]
New word: star
Label:
```

| Independent request | Actual reply | Format check |
|---|---|---|
| New word: star | `[STAR]` | Matched the requested capital-letter pattern. |
| New word: moon | `[Moon]` | **Mismatch:** only the first letter was capitalized. |
| Fresh star request | `[STAR]` | Matched again. |

The changed response is intentionally preserved exactly. We did not silently replace it with `[MOON]`. One example can guide output, but even these simple requests needed checking. The results do not establish general reliability or factual accuracy.

An adult who already has this model installed in a local Ollama instance can reproduce a request using the loopback API; no paid service or personal information is needed:

```python
import json
from urllib.request import Request, urlopen

prompt = """Make a museum label using the same bracket and capital-letter pattern as the example.
Example: fox -> [FOX]
New word: star
Label:"""
payload = {
    "model": "llama3.2:3b",
    "messages": [
        {"role": "system", "content": "Return only the new label."},
        {"role": "user", "content": prompt},
    ],
    "stream": False,
    "options": {"temperature": 0, "seed": 141, "num_predict": 40},
    "keep_alive": 0,
}
request = Request("http://127.0.0.1:11434/api/chat",
                  data=json.dumps(payload).encode(),
                  headers={"Content-Type": "application/json"})
with urlopen(request, timeout=90) as response:
    print(json.load(response)["message"]["content"])
```

Change only the new word to moon for a new independent request. Compare what actually returns; your result can differ from this recording.

### Count agreement — scripted toy votes

Group A is `star, star, moon`: 2 of 3 support star. Group B is `star, star, star`: 3 of 3 support star. B has more agreement, but all three could share a mistake. These are invented votes, not model executions or probabilities of truth. Check independent evidence.

## 4. Read-only access and a changed case — Linux

Return to the same disposable Linux directory created above. Predict which operation should fail:

```sh
chmod 400 label.txt
cat label.txt
printf EXTRA >> label.txt
sha256sum label.txt
```

The ordinary owner read `STAR EXHIBIT`; appending failed with `Permission denied`; the contents and hash remained unchanged. A separate mode-600 control accepted an append:

```sh
printf ORIGINAL > control.txt
chmod 600 control.txt
printf EXTRA >> control.txt
cat control.txt
```

The control returned `ORIGINALEXTRA`. This is a file-mode exercise, not an unbreakable security boundary: the owner can change an owned file's mode, and directory permissions also matter.

Now change the filename while retaining its contents and mode:

```sh
mv label.txt moon.txt
find . -name 'moon.txt'
cat moon.txt
stat -c %a moon.txt
test ! -e label.txt
sha256sum moon.txt
```

Recorded output includes `./moon.txt`, **`STAR EXHIBIT`**, and mode `400`. A new filename does not rewrite the exhibit words. We describe it honestly as a star exhibit stored in a file named moon. A fresh shell independently confirmed the result.

The changed Ansible visitor and exhibit values were tested separately. Ansible did not secretly read the Linux file, validate a model reply, or open a physical door.
