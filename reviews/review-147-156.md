## 1. Find the right object and read saved evidence

Requirements: an ordinary Linux user and GNU find/coreutils. Do not use system directories or personal files. Create the complete practice fixture:

```sh
station_practice=$(mktemp -d)
cd "$station_practice"
mkdir -p files folders/report.txt
printf 'STATION: Harbor\nDEPARTURE: unknown\n' > files/report.txt
printf '07:00 setup\n07:01 copied\n07:02 waiting\n07:03 check paused\n' > report.log
```

Predict before each command:

```sh
find . -name 'report.txt' -printf '%y %p\n' | sort
find . -type f -name 'report.txt'
tail -n 2 report.log
tail -n 1 report.log
```

The broad name query returned a directory (`d ./folders/report.txt`) and a regular file (`f ./files/report.txt`). `sort` is used only to make the displayed name/type list deterministic. The type-filtered query returned only `./files/report.txt`.

`tail -n 2` returned `07:02 waiting` and `07:03 check paused`. Changing only the count to one returned just `07:03 check paused`. Tail selects saved lines in file order; it does not sort times or query live status.

## 3. Template and condition — separate localhost Ansible

In a separate empty practice directory, save `station.yml`:

```yaml
- hosts: localhost
  connection: local
  gather_facts: false
  vars:
    station: Harbor
    status: waiting
  tasks:
    - name: Station heading
      ansible.builtin.debug:
        msg: "Station: {{ station }}"
    - name: Ready message
      ansible.builtin.debug:
        msg: REPORT READY LOCALLY
      when: status == 'ready'
```

Use an existing Ansible installation. No remote inventory, gathered facts or privilege escalation is involved:

```sh
ansible-playbook -i localhost, --limit localhost station.yml --syntax-check
ansible-playbook -i localhost, --limit localhost station.yml
```

The base heading was `Station: Harbor`; the ready message was skipped. Test each change independently from the base:

## 4. Bounded retries — another disposable local fixture

In a new empty directory save `checker.py`:

```python
"""Disposable local readiness simulator. Only writes its supplied trace file."""
from pathlib import Path
import json,sys
trace=Path(sys.argv[1]);ready_on=int(sys.argv[2])
rows=trace.read_text().splitlines() if trace.exists() else []
n=len(rows)+1;ready=n>=ready_on
row={'try':n,'state':'READY' if ready else 'WAIT'}
with trace.open('a') as f:f.write(json.dumps(row)+'\n')
print(row['state'])
sys.exit(0 if ready else 1)
```

Save `retry.yml` alongside it:

```yaml
- name: Bounded local readiness simulation
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    ready_on: 3
  tasks:
    - name: Check simulated readiness
      ansible.builtin.command:
        argv:
          - "{{ ansible_playbook_python }}"
          - "{{ playbook_dir }}/checker.py"
          - "{{ playbook_dir }}/trace.jsonl"
          - "{{ ready_on }}"
      register: check
      until: check.rc == 0
      retries: 2
      delay: 1
    - name: Only reached after success
      ansible.builtin.debug:
        msg: REPORT CHECK READY
```

The checker writes only its supplied trace file. Run once with no existing `trace.jsonl`:

```sh
ansible-playbook -i localhost, --limit localhost retry.yml
cat trace.jsonl
```

The actual trace was `WAIT, WAIT, READY`. The initial call plus two retries made three total calls, then the next task printed `REPORT CHECK READY`.

For a separate fresh case, remove only the trace you just created and change only `ready_on: 3` to `ready_on: 4`. The recorded trace was `WAIT, WAIT, WAIT`; the play failed and never reached the next task. It did not make a fourth call. A fresh base replay succeeded; an early-success control with `ready_on: 1` made just one call.

Count actual trace entries when discussing total calls. Ansible's registered failed-attempt count can differ from that total. This is a toy local simulation, not a real service test. Retries do not make unsafe or non-repeatable actions safe.

## 7. A tie and an authored rule

The fictional votes are `blue, gold, blue, gold`. Our explicitly authored rule is to abstain on a tie. Two of each means `ABSTAIN`. Changing only the last gold to blue gives three blue and one gold, so the same rule chooses `BLUE`.

This is a scripted counting exercise, not a calibrated probability or proof that a color label is true. We are demonstrating a decision rule, not hiding its limits.

## 8. Read versus directly execute — ordinary Linux user

Back in the disposable Linux directory, create the exact harmless script:

```sh
printf '#!/bin/sh\nprintf "REPORT CHECKED\\n"\n' > inspect.sh
chmod 400 inspect.sh
cat inspect.sh
sha256sum inspect.sh
./inspect.sh
```

Reading succeeded; direct start failed with `Permission denied`. Add only owner execute permission and try again:

```sh
chmod 500 inspect.sh
./inspect.sh
sha256sum inspect.sh
```

The output was `REPORT CHECKED`; the script hash was unchanged. A fresh mode-400 case denied direct execution again. A separate control **did run at mode 400** through a shell:

```sh
chmod 400 inspect.sh
sh inspect.sh
```

This distinction matters: read-only permission is not a sandbox that prevents all ways of running readable code. The owner can also change their owned file's mode. Never experiment on system scripts, somebody else's files or untrusted code.
