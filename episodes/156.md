# Episode 156 — Ready in Time?

Our pretend rocket needs a ready signal. A disposable toy checker returns `WAIT` until a chosen try. Ansible runs it once and allows two retries, with a one-second delay between attempts. Predict the outcome before running each case.

| Case in a fresh folder | Ready on try | Observed trace | Outcome |
| --- | --- | --- | --- |
| Base | 3 | WAIT, WAIT, READY | Task succeeds; next message runs |
| Change only readiness | 4 | WAIT, WAIT, WAIT | Task fails; no fourth try or next message |
| Fresh replay | 3 | WAIT, WAIT, READY | Same success |
| Early-success control | 1 | READY | Stops after the first try |

These cases actually ran on localhost with Ansible Core 2.18.5. Each invocation of the checker appended one line to its disposable trace, so the table counts real calls. The failed run reported `attempts: 2` in its registered result while the trace contained three calls; do not confuse that field with the total number of calls in this version. The trace, exit status and presence or absence of the next task were checked independently. The changed case exited unsuccessfully as intended; it was not hidden with `ignore_errors` or converted to success. All production temporary folders were removed.

## Try with a grown-up

Use an existing Python and Ansible practice environment. Create a new temporary folder and save the following two files there. The checker writes only its own `trace.jsonl` file. No real rocket, device, service or network request is involved.

`checker.py`:

```python
"""Disposable local readiness simulator. Only writes its supplied trace file."""
from pathlib import Path
import json,sys
trace=Path(sys.argv[1]);ready_on=int(sys.argv[2])
rows=trace.read_text().splitlines() if trace.exists() else []
n=len(rows)+1;ready=n>=ready_on
row={'try':n,'state':'READY' if ready else 'WAIT'}
with trace.open('a') as f:f.write(json.dumps(row)+'\n')
print(row['state'])
sys.exit(0 if ready else 1)
```

`demo.yml`:

```yaml
- name: Bounded local readiness simulation
  hosts: localhost
  connection: local
  gather_facts: false
  vars:
    ready_on: 3
  tasks:
    - name: Check simulated readiness
      ansible.builtin.command:
        argv:
          - "{{ ansible_playbook_python }}"
          - "{{ playbook_dir }}/checker.py"
          - "{{ playbook_dir }}/trace.jsonl"
          - "{{ ready_on }}"
      register: check
      until: check.rc == 0
      retries: 2
      delay: 1
    - name: Only reached after success
      ansible.builtin.debug:
        msg: SIMULATED LAUNCH READY
```

From that new folder, syntax-check and run only localhost:

```sh
ansible-playbook -i localhost, --limit localhost demo.yml --syntax-check
ansible-playbook -i localhost, --limit localhost demo.yml
cat trace.jsonl
```

The simulator counts existing trace rows, so **use a fresh folder for each case**. Change only `ready_on: 3` to `ready_on: 4`, leaving `until`, `retries` and `delay` identical. Predict success or failure, run, and inspect the trace. An unsuccessful playbook exit is expected for this changed case. Repeat the base in a new process and folder. A separate `ready_on: 1` control demonstrates that the checker stops early on success instead of always using all available tries.

The video shows the retry configuration excerpt and a readable summary of the recorded trace, not a complete playbook or fabricated console transcript. `register` saves the task result, `until` tests it, `retries` bounds repeat attempts, and `delay` spaces them. Here return code zero means this toy checker is ready. Other tasks can use different success conditions.

A retry limit does not make an action safe or idempotent. Repeating a payment, sending a message or launching a real process may create extra side effects. This example only appends disposable trace rows. It is not a recovery policy, timeout guarantee, production monitor or real launch controller.
